## High

**H1. `hoan_tac` is not an undo stack. A second undo re-applies the same op, and for `gop`/`xoa_kieu` it crashes with a 500.** models_chia.py:563-566 always picks the latest row in `_HOAN_TAC_DUOC`. `hoan_tac` rows are not in that set, and nothing marks the original op as already undone.
- Probe: gop A→B, then undo → OK. Undo again → `IntegrityError UNIQUE constraint failed: cum_nhap.id`. `sqlite3.IntegrityError` is not a `ValueError`, so the route returns an unhandled 500.
- Probe: rename a→a2, rename b→b2, undo, undo → `['a2','b']`. The first rename can never be undone. Each extra click also writes one more `hoan_tac` row, which inflates the D15 count.
- Fix: in the query, skip ops that already have a `hoan_tac` row pointing at them, e.g. `AND id NOT IN (SELECT json_extract(chi_tiet_json,'$.hoan_tac_id') FROM thao_tac_duyet WHERE chia_lan_id=? AND loai='hoan_tac')`. Add tests for "2 undos = 2 ops back" and "undo with nothing left ⇒ 409, not 500".

**H2. `hoan_tac` crosses boundaries it must not cross.** There are two cases:
- (a) **After approve.** Probe: gop A→B, then duyet_het (the lot becomes `da_duyet`), then hoan_tac → succeeds. Kiểu `a` comes back as a pending draft inside a `da_duyet` lot, holding a video that is already in a real cluster. D14b stops it from moving again, so the `cum` table stays safe. But the lot state is now inconsistent: it says `da_duyet` while a draft is still pending. `ap_thao_tac`, `duyet_kieu` and `duyet_het` never check `trang_thai`; only `ghi_de_xuat` does (line 100). `huy` is not guarded anywhere either.
- (b) **After a new proposal.** Probe: xoa_kieu a, then `ghi_de_xuat` writes a new proposal "moi"=[1,2], then hoan_tac → **resurrects kiểu `a` from the previous proposal** and pulls video 1 out of "moi". Result: `[('a',['1']),('moi',['2'])]`.
- Fix: reject every edit op and every approve when `trang_thai ∉ {de_xuat}`. Also limit hoan_tac to ops logged after the latest `ghi_de_xuat` (store a marker, or bump a `the_he` column on `chia_lan`).

**H3. JS handoff now `await`s a fetch before `window.open`, and non-session errors fail silently.** app.js:1117-1136.
- (a) **Popup risk.** The old path called `window.open` synchronously inside the click. Now it runs only after `await apiGet(...)`. Chromium keeps transient activation for about 5 s, so this usually still works. It gets blocked if the mini is slow (more than 5 s). **Safari is CHƯA ĐO (not measured).** Safari is known to be stricter about popups opened after an await. The Playwright test runs headless Chromium, which allows popups regardless, so no existing test can see this. Failure mode: the user sees "Trình duyệt đã chặn tab mới — cho phép popup", but popups are already allowed.
- (b) **Silent failure.** Any error other than `PhienHetHan` is re-thrown, and the caller (`moLoCum(...).then(...)` at app.js:827, and `moHetLoCum` at 1152) has no `.catch`. Result: an unhandled rejection and no toast. Concrete case: a video was removed in another tab, so the server's `so_lo` is now 2 while the UI still shows "Bộ 3" → the route returns 400 → the click does nothing.
- Fix: open a blank tab synchronously first (`const tab = window.open("", "_blank")`), fetch, then set `tab.location = url`, or `tab.close()` on error. Also add a `.catch` that shows a toast. At minimum, manually test once on Safari before merge.

## Medium

**M1. Two-tier naming collapses at approve time. The same kiểu name under two different nhóm collides with a cluster created in the same request.** `_giai_quyet_kieu` names the cluster from `kieu` only; `nhom` is dropped (line 251).
- Probe: nhóm "ao dai"/couple=[1] and nhóm "vest"/couple=[2], then duyet_het → the first creates cum 1. The second is returned as `trung_cum_co_san` pointing at **cum 1, which was created milliseconds earlier in the same call**. The user is asked to "confirm merge" into a cluster they never saw.
- D1 (nhóm → kiểu) makes this likely. The vision layer will reuse kiểu names across nhóm.
- Needs a decision (see Q1). At minimum, `duyet_het` should skip the D13 prompt for clusters it created itself in the same call, or reject duplicate kiểu names within a lot at `ghi_de_xuat`/`doi_ten`.

**M2. `doi_insight` writes `jobs` without checking who owns the job.** models_chia.py:221-222 and 554-555 run `UPDATE jobs … WHERE id = lan.job_id`. `tao_chia_lan` (55-74) never checks `jobs.nguoi_tao = chu`.
- Probe: admin creates a lot on toi@'s job and runs doi_insight → toi@'s `jobs.usecase` becomes "X".
- If two users (admin plus owner) split the same job, they overwrite each other's defaults. Latent now (no route calls `tao_chia_lan` in p1), but it becomes live in phase 2.
- Fix: in `tao_chia_lan`, require the job's owner to be `chu` (or admin, as an explicit decision). Only write back to `jobs` when `jobs.nguoi_tao = chu`.

**M3. Route `POST /chia/{id}/thao-tac` returns 500 when a required parameter is missing.** Probe: `{"loai":"gop"}` → `TypeError: _op_gop() missing 2 required positional arguments`. The same happens for chap_nhan/doi_ten/xoa_kieu without `cum_nhap_id`, and for chuyen/tra_ve without `den_cum_nhap_id`. Fix: catch `TypeError` in `ap_thao_tac` and treat it as `tu_choi`, or give every parameter a `None` default and return None.

**M4. Videos are dropped silently at approve.** `ghi_de_xuat` never checks that ids exist, belong to the job, or belong to `chu`. Probe: `video_ids=["1","NOPE"]` gives `da_o_cum: []`. At approve, the `hop_le` filter (lines 271-278) drops "NOPE" and videos already removed from the library, and they appear neither in `gan` nor in `da_o_cum`. Their `video_cum_nhap` rows are left with `cum_nhap_id=NULL, lan='kieu'`, and `lay_chia` does not show them (line 172). The video disappears from the UI with no trace. Fix: add a `bo_qua` list to the result and the log; validate ids against `videos.job_id = lan.job_id` at `ghi_de_xuat`.

**M5. One bad kiểu name aborts all of "Duyệt tất cả".** `kiem_nhan` raises inside the loop (line 251), so everything rolls back and returns 400 "tên insight con … quá 120 ký tự" without saying which kiểu. Neither `ghi_de_xuat` nor `_op_doi_ten` checks length. Fix: validate with `kiem_nhan` at write time (given an insight), or return an error per kiểu the way `trung` is returned.

**M6. `_giai_quyet_kieu` re-implements `tao_cum` + `gan_video` and uses the private `_cum_trung`, which invites drift.** I checked today's equivalence and found it faithful: `kiem_nhan`, `_cum_trung`, the INSERT columns, and the `hop_le` filter all match, and the upsert SQL is the same. The atomicity argument is correct: `gan_video` opens its own connection without `BEGIN IMMEDIATE`, so two separate calls would reopen the D14b race. But nothing pins the equivalence. A future change to `gan_video`'s filter or to `tao_cum`'s columns would diverge silently. Fix, in the next phase that may touch models_cum: extract conn-level `_tao_cum_tren(conn,…)`/`_gan_video_tren(conn,…)` used by both. Now: add a test that runs `tao_cum` + `gan_video` and `duyet_kieu` on twin DBs and compares the `cum`/`video_cum` rows.

**M7. The "byte-equal" D7 test is weaker than its name.** test_web_chia.py:236-279 re-ports the old JS in **Python with the same SQL as the server** and compares with `sort_keys=True`. It does not prove key order, and it does not execute the old JS. The JS harness (tests/js/cum-ban-giao.js) mocks `apiGet` with a JS re-implementation, so it never tests the server. My own reading: key order (`v,items,nhan` / `usecase,insight,template,cum_id,lo{thu,tong}`) and value rules (`title||video_id`, drive truthiness) do match, so bytes are equal in steady state. They differ only when `state.videos` is stale or truncated at LIBRARY_MAX. There the server is more correct, but the UI's lot labels, the `muc.length`-based toast, and `lo_mo` markers are still computed locally, so they can disagree with what was actually sent. Fix: drop `sort_keys`, and compare against a golden string produced by running the old `nhanTuCum`/`dungPayload` in node.
